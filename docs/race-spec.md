# 순위 정하기 게임 — 최종 통합 개발 지시서

## 1. 역할 및 목표

당신은 **로컬 Codex 개발 에이전트**입니다.

현재 구현된 순위 정하기 게임을 다음과 같은 **3단계 물리 기반 레이싱 게임**으로 확장하세요.

기존 기능을 최대한 재사용하고, 기능 구현부터 테스트, 오류 수정, 최종 검증까지 수행하세요.

### 최종 목표

1. 경기 준비와 실제 출발을 분리
2. 1단계 하강 → 컨베이어 → 2단계 상승 → 3단계 최종 하강
3. 2단계에서 1단계로 돌아가는 역회전 회전문 구현
4. 3단계에서 2단계로 돌아가는 역회전 회전문 구현
5. 물리 충돌에 따른 자연스러운 속도 차이와 순위 역전
6. 팀 이름·조원 사진·게임 설정 영속화
7. Slack Webhook 설정 저장 및 경기 결과 자동 전송
8. 경기 종료 후 팀 정보 유지 및 재경기 지원
9. Playwright 테스트와 기존 기능 회귀 검증
10. 모든 작업 완료 후 Git 커밋 및 결과 보고

**최우선 원칙: 순위는 미리 결정하거나 임의 조작하지 않으며, 실제 물리 시뮬레이션 결과로만 결정합니다.**

# STEP 1. 경기 상태 및 화면 전환 개선

## 1.1 경기 상태

다음 상태를 정의하세요.

```text
IDLE
  ↓
READY
  ↓
RUNNING
  ↓
FINISHED
```

### IDLE — 관리자 설정

- 팀 등록
- 조원 사진 등록
- 장애물 설정
- 게임 난이도 설정
- Slack 설정
- 시작 위치 셔플 설정

### READY — 경기 준비

관리자가 경기 준비 버튼을 클릭하면 게임 화면으로 이동합니다.

이 상태에서:

- 모든 공이 1단계 상단 출발대에 정렬
- 각 공에 팀 이름 또는 팀 식별 정보 표시
- 기존과 동일하게 첫 번째 조원 사진 표시
- 공은 출발 전까지 고정
- 장애물·회전문·컨베이어는 계속 애니메이션
- 경기 시간은 아직 측정하지 않음
- 화면에 큰 '출발' 버튼 표시

### RUNNING — 실제 출발

출발 버튼 클릭 시:

- 모든 공을 동시에 해제
- 중력 및 충돌 시뮬레이션 시작
- 실제 경과 시간 측정
- 출발 버튼 숨김
- 중복 출발 방지

### FINISHED — 경기 종료

모든 공이 결승선에 도착하면:

- 최종 순위 확정
- 팀 이름·사진 표시
- 소요 시간 표시
- 충돌 횟수 표시
- 단계별 복귀 횟수 표시
- Slack 전송 처리
- 다시 경기하기 버튼 제공

경기 상태 전환은 중복 이벤트가 발생해도 안전하게 처리하세요.

# STEP 2. 3단계 레이싱 화면 구현

## 2.1 전체 경로

```text
       1단계            2단계             3단계
       하강 ↓            상승 ↑            하강 ↓

    ┌─────────┐      ┌─────────┐      ┌─────────┐
    │ START   │      │         │─────→│         │
    │   ↓     │      │    ↑    │      │    ↓    │
    │ 장애물  │      │ 상승패들│      │ 장애물  │
    │   ↓     │      │    ↑    │      │    ↓    │
    │ 장애물  │      │ 복귀문  │      │ 복귀문  │
    │   ↓     │      │    ↑    │      │    ↓    │
    │         │─────→│         │      │ FINISH  │
    └─────────┘      └─────────┘      └─────────┘

    복귀문:
    2단계 → 1단계
    3단계 → 2단계
```

위 그림은 논리 구조만 표현한 것입니다.

실제 화면에서는 정상 경로와 복귀 통로가 서로 충돌하지 않도록 물리적 공간을 확보하세요.

## 2.2 Canvas 정책

기존 800×600 단일 낙하판을 3단계에 맞게 확장합니다.

권장 방향:

- 가로로 넓은 Canvas 구성
- 논리 좌표와 실제 출력 크기 분리
- 화면 비율 유지
- 고해상도 디스플레이 지원
- 팀 이름과 사진 가독성 확보
- 전체 경로를 한 화면에서 관찰할 수 있도록 구현

화면이 좁아지더라도 물리 엔진의 좌표나 충돌 결과가 달라지지 않아야 합니다.

# STEP 3. 1단계 — 하강

1단계는 기존 단일 낙하 구조를 최대한 재사용하세요.

### 기능

- 상단 출발대에서 모든 공 동시 출발
- 중력 적용
- 고정 장애물 충돌
- 회전 장애물 충돌
- 좌우 이동 장애물 충돌
- 충돌에 따른 경로·속도 변화

### 장애물 기본 배치

공이 시작점에서 아래까지 장애물을 전혀 만나지 않고 수직으로 통과하는 직선 경로를 방지하세요.

- 엇갈린 경사판
- 회전 장애물
- 좌우 이동 장애물

단, 공이 영구적으로 끼이거나 모든 공이 동일한 경로만 반복하는 구조는 피하세요.

# STEP 4. 하단 컨베이어

1단계 하단과 2단계 하단을 연결하는 컨베이어를 구현하세요.

### 동작

1. 공이 1단계 하단에 도착
2. 컨베이어에 진입
3. 벨트가 공을 오른쪽으로 이동
4. 2단계 상승 구간으로 자연스럽게 연결

### 필수 조건

- 컨베이어 표면이 움직이는 애니메이션
- 공마다 진입 시각이 다를 수 있음
- 먼저 진입한 공을 다른 공이 기다리게 하지 않음
- 공 간 충돌 정책을 기존 엔진과 일관되게 적용
- 컨베이어 이동 중 벽 관통 방지
- 공이 연결부에서 끼이지 않도록 처리

컨베이어는 팀별 속도 지정 방식이 아니라 동일한 벨트·접촉 규칙을 사용하세요.

# STEP 5. 2단계 — 회전 패들 상승

2단계에서는 공이 아래에서 위로 이동합니다.

## 5.1 회전 패들

좌우 벽에 여러 개의 회전 패들을 엇갈리게 배치하세요.

패들이 공을 위쪽으로 밀어 올리는 물리적 동작을 구현합니다.

### 요구사항

- 패들 각속도 및 회전 방향 정의
- 공과 패들 사이 충돌 검출
- 충돌 방향을 기준으로 반발 속도 계산
- 접촉 타이밍에 따른 상승 속도 차이
- 상승 도중 순간적인 하강 허용
- 공이 충분히 상승하면 상단 연결부로 이동

### 순위 역전

같은 물리 규칙 아래에서도 다음과 같은 차이가 발생해야 합니다.

- 어떤 공은 패들을 정확하게 맞고 빠르게 상승
- 어떤 공은 옆으로 튕겨 잠시 정체
- 어떤 공은 다음 패들을 기다렸다가 상승
- 뒤늦게 들어온 공이 먼저 상단에 도착

**공마다 상승 속도를 임의로 지정하지 마세요.**

패들만으로 안정적인 상승이 불가능한 경우, 모든 공에 동일하게 적용되는 보조 상승 장치를 추가할 수 있습니다.

# STEP 6. 2단계 역회전 회전문 — 1단계 복귀

2단계 상단 방향 약 60~80% 진행 지점에 역회전 회전문을 배치하세요.

## 6.1 기본 동작

- 회전문은 일정한 각속도로 회전
- 공이 회전문에 접근
- 회전문 날개의 위치와 충돌 각도에 따라 진행 방향이 달라짐
- 정상 통과한 공은 계속 상승
- 복귀 방향으로 튕겨진 공은 1단계 복귀 통로로 진입

### 복귀 경로

```text
2단계 상승
     ↑
 역회전 회전문
     ├── 정상 통과 → 2단계 상단
     │
     └── 복귀 통로 → 1단계
```

복귀한 공은 1단계의 지정된 상부 진입 지점에서 다시 하강합니다.

### 구현 원칙

- 회전문 충돌 결과로 복귀 여부 결정
- 임의 확률값으로 복귀 팀 선정 금지
- 팀 ID·팀 이름·현재 순위에 따른 차등 처리 금지
- 실제 복귀 경로를 화면에서 확인 가능해야 함
- 순간이동 대신 연속된 통로 이동 구현
- 복귀 횟수 기록

---

# STEP 7. 3단계 역회전 회전문 — 2단계 복귀

3단계 중상단에 역회전 회전문을 배치하세요.

## 7.1 기본 동작

3단계에서 공은 아래로 낙하합니다.

회전문과 충돌하면 접촉 위치와 타이밍에 따라 다음 두 가지 동작이 발생합니다.

### 정상 통과

공이 회전문을 지나 계속 아래로 낙하합니다.

### 복귀

회전문에 의해 왼쪽 복귀 통로로 밀려 2단계 하부의 지정된 재진입 지점으로 이동합니다.

```text
3단계 하강
     ↓
 역회전 회전문
     ├── 정상 통과 → 결승선
     │
     └── 복귀 통로 → 2단계 하부
                        ↓
                    다시 상승
```

### 주의사항

2단계 복귀문과 3단계 복귀문은 별도의 장치입니다.

- 2단계 복귀문: 1단계로 복귀
- 3단계 복귀문: 2단계로 복귀

3단계에서 곧바로 1단계로 복귀시키는 구조는 구현하지 마세요.

### 복귀 통로

복귀 통로는 일반 경기 경로와 구분하여 렌더링하세요.

- 시각적으로 구분되는 색상
- 이동 방향 표시
- 자연스러운 물리적 이동
- 공의 크기보다 충분히 넓은 통로
- 다른 장애물과 충돌하지 않는 설계
- 공이 통로에서 영구 정체되지 않도록 구성

3단계의 복귀 통로는 2단계 하부의 상승 진입부까지 연속적으로 연결해야 합니다. 중력만으로 상향 이동이 불가능한 경로에는 모든 공에 동일하게 작동하는 기계식 컨베이어나 리프트를 사용하세요.

# STEP 8. 복귀 횟수 및 무한 루프 방지

## 8.1 기본 정책

공별 복귀 정보를 관리하세요.

```javascript
{
  stage: 1,
  returnCount: 0,
  returnFromStage2: 0,
  returnFromStage3: 0,
  maxReturns: 2,
  returnCooldown: 0
}
```

### 초기 기본값

- 총 복귀 가능 횟수: 2회
- 복귀 직후 보호시간: 1초
- 최대 복귀 횟수 초과 시 정상 경로로 유도
- 복귀 횟수는 경기마다 초기화
- 복귀 통계는 최종 결과에 포함

복귀 한도를 초과한 공은 복귀문에 의해 다시 이전 단계로 들어가지 않도록 동일하게 적용되는 정상 진행 통로로 유도하세요.

다른 공이나 장애물을 관통하도록 만들지는 마세요.

## 8.2 관리자 설정

다음 설정을 추가하세요.

| 설정 | 기본값 |
|---|---|
| 역회전 복귀문 사용 | ON |
| 2단계 복귀문 | ON |
| 3단계 복귀문 | ON |
| 최대 복귀 횟수 | 2 |
| 복귀 보호시간 | 1초 |
| 난이도 | 보통 |

### 난이도

**쉬움**
- 회전문 접촉 가능 구간 축소
- 최대 복귀 1회

**보통**
- 복귀문 단계별 1개
- 최대 복귀 2회

**어려움**
- 회전문 속도 및 복귀 유도 구간 확대
- 최대 복귀 3회

난이도 변화는 모든 공에 동일하게 적용하세요.

3단계는 정상 경로를 따라 최종적으로 하강하는 구간입니다.

- 결승선을 통과한 공은 다시 복귀하지 않음

# STEP 10. 팀 이름·사진 영속화

## 10.1 목표

관리자가 한 번 등록한 팀 이름과 조원 사진은 이후 다시 접속해도 유지되어야 합니다.

### 저장 대상

- 팀 ID
- 팀 이름
- 팀원 정보
- 등록된 조원 사진
- 팀 등록 순서
- 시작 위치 셔플 설정
- 관리자 경기 설정
- 장애물 사용자 설정
- 난이도
- 복귀문 활성화 및 최대 복귀 횟수

### 저장 방식

**IndexedDB를 기본 저장소로 사용하세요.**

사진은 Blob 형태로 저장합니다.

권장 데이터 구조:

```text
IndexedDB
 ├── teams
 ├── members
 ├── photos
 └── gameSettings
```

실제 구조는 기존 데이터 모델을 분석해 결정하세요.

### 동작

- 팀 등록 시 자동 저장
- 사진 등록 시 자동 저장
- 수정·삭제 시 자동 반영
- 페이지 새로고침 후 복원
- 브라우저 재실행 후 복원
- 관리자 화면 재방문 시 자동 표시
- 경기 종료 후 정보 유지

### 오류 처리

- IndexedDB 사용 불가
- 저장 공간 부족
- 사진 데이터 손상
- 저장 작업 중 브라우저 종료
- 기존 데이터와 스키마 충돌

위 상황에서 앱 전체가 중단되지 않도록 처리하고, 저장 실패 시 관리자에게 표시하세요.

사진 Blob URL은 필요할 때 생성하고 더 이상 사용하지 않으면 해제하여 메모리 누수를 방지하세요.

# STEP 11. Slack 설정 영속화 및 보안

## 11.1 목표

관리자가 Slack Incoming Webhook URL을 설정하면 이후 재접속 시에도 동일한 브라우저에서 사용할 수 있도록 합니다.

단, Webhook URL은 메시지 전송 권한을 가진 비밀 값이므로 저장 방식과 노출 위험을 고려해야 합니다.

### 저장 정책

- 관리자가 명시적으로 '이 브라우저에 저장'을 선택한 경우에만 저장
- 기존 URL 조회 및 변경 가능
- 저장된 URL은 화면에서 마스킹
- 저장된 Webhook 삭제 기능 제공
- 브라우저 새로고침 후 설정 복원
- 경기 종료 후 URL 유지
- 콘솔·테스트 로그·오류 메시지에 전체 URL 출력 금지
- Git 저장소에 Webhook 값 기록 금지

별도 백엔드가 없는 현재 구조에서는 브라우저 저장소에 보관한 Webhook이 해당 브라우저 환경에 접근할 수 있는 사용자나 코드에 노출될 수 있음을 관리자 화면에 명시하세요.

브라우저 내 암호화만으로 이 위험이 해결된다고 안내하지 마세요.

### Slack 전송

- 경기 결과가 확정되면 자동 전송 시도
- 경기당 중복 전송 방지
- 전송 성공·실패 상태 표시
- 실패 시 수동 재전송 허용
- 실패해도 경기 결과는 정상 표시
- 실제 전송이 성공한 경우에만 성공으로 표시
- CORS 등 브라우저 직접 전송 제한이 있다면 원인을 보고하고 기존 지원 가능한 구조를 유지

실제 Slack 전송의 HTTP 응답을 확인할 수 없는 경우 성공으로 간주하지 마세요.

보안상 실제 Webhook을 테스트에 사용하지 말고 Mock으로 검증하세요.

# STEP 14. 물리 엔진 안정화

이번 개발에서 가장 중요한 기술적 검증 항목입니다.

### 필수 조건

1. 프레임레이트에 따른 결과 편차 최소화
2. 고정된 물리 시간 간격 사용
3. 공과 장애물 충돌 안정화
4. 회전 패들에 의한 비정상 가속 방지
5. 벽 관통 방지
6. 복귀문 중복 작동 방지
7. 컨베이어 끼임 방지
8. 상승 구간 장기 정체 방지
9. 복귀 통로 교착 방지
10. 모든 공의 경기 완료 가능성 확보

### 정체 처리

공이 일정 시간 이상 이동하지 않으면 원인을 판단하고 기존 물리 규칙과 일관된 복구 방식을 적용하세요.

특정 팀을 강제로 앞으로 이동시켜 순위를 바꾸는 방식은 금지합니다.

복구가 불가능한 경우 해당 공을 무작정 완주 처리하지 말고, 경기 상태에 오류 또는 미완주로 표시하세요.

### 경기 제한시간

기본 경기 최대 시간은 90초로 설정합니다.

90초는 초기 설정값이며 관리자 변경을 허용합니다.

시간 초과 시:

- 도착한 공의 순위 유지
- 미도착 공은 DNF(미완주) 표시
- 시간 초과 및 원인 기록
- 미도착 공을 임의 순위로 처리하지 않음
- DNF를 포함하여 결과 화면과 Slack에 일관되게 표시
